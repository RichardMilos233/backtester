Agent Infra Benchmark：现状与未来方向

用可重复、与行情无关的方式比较"不同 LLM × 不同 agent 架构"在交易策略参数搜索上的能力。本文记录当前协议、已有结论，以及参考 Financial Audit Bench 后的改进方向。

01我们在比什么

一个 agent 被丢进一个标的和一段日期里，手里只有有限的回测次数。它每轮提出一个策略 spec（信号类型、回看窗口、波动率目标），系统回测后把验证集夏普反馈给它。预算用完后，它选验证集最好的 spec 交卷，我们在测试集上评一次。

比的不是"谁的测试集夏普高"，而是"在给定反馈下，谁能找到更好的 spec"。前者大部分由行情决定，后者才是 agent 能控制的。

Task一个标的 + 一段日期；内部按 60/20/20 切 Train / Val / Test
Proposeagent 输出一个 spec；Reviewer 可打回（不计预算）
Backtest回测 Val，返回夏普等指标；消耗 1 次预算
Select预算耗尽后，按 Val 夏普选最终 spec
Score对照 oracle 换算成分位数；Test 只评一次

一次运行的单位

运行键
(task_id, model, framework_type, seed)
预算
送进回测的 spec 数 max_backtests，不是 LLM 调用数
架构
B（单 Researcher）、C（Researcher + Reviewer）、C-sota、C-corr、C-hier
产出
一行 summary.csv + 一条带完整 trajectory 的 runs.jsonl

02怎么打分：Oracle 归一化

每个任务先用 scripts/build_oracle.py 把搜索空间里全部 12,020 个 spec（259 个动量窗口 + 2,145 个 MACD 格点，各 × 5 档波动率缩放）在 Val 和 Test 上跑一遍。有了全空间分布，agent 的选择就能换算成与行情无关的分数。

列含义作用
percentile_val选中 spec 在全空间 Val 夏普中的分位主指标：搜索质量
regret_test全空间 Test 最优夏普 − 选中 spec 的 Test 夏普离天花板多远
regret_vs_val_oracle"全知 Val 选择器"的 Test 夏普 − 选中 spec 的 Test 夏普负值 = 运气好过天花板
percentile_test选中 spec 在全空间 Test 夏普中的分位参考
on_latticespec 是否落在格点上不在则直接回测取值
为什么主指标不是 Test 夏普。在 SPY_full 上，全空间 Val 夏普与 Test 夏普的 Spearman 相关只有 −0.13。Val 最好的 spec 在 Test 上只排中游。Test 夏普高低基本不反映搜索能力，只反映行情是否恰好奖励了那类参数。

必须一起跑的非 LLM 基线

  • R-random：同预算，从全格点均匀抽样。
  • R-grid：同预算，格点上等距取点，与种子无关。

LLM 架构要进榜，先要在 percentile_val 上稳定赢过 R-random。

03任务集

套件任务用途
smokeSPY_full回归、调试；等于 Phase 1/2 的原始设置
coreSPY w1/w2/w3、QQQ_w2、IWM_w2、TLT_w3、GLD_w1、SYNTH_RW_full日常比较，8 个任务
full6 个 ETF × 3 窗口 + SYNTH_RW定稿

滚动窗口让 Test 落在不同行情：w1 ≈ 疫后单边上涨，w2 ≈ 2022 熊市 + 震荡，w3 ≈ 2024 至今。SYNTH_RW 是零漂移随机游走，任何策略都不该有稳定 alpha，用来测 agent 会不会追噪声。

汇总规则

  1. 同一 (task, model, infra) 先对种子取均值。
  2. 再跨 task 取均值，每个 task 等权。
  3. 排名用 percentile_val；并列报 regret_test、对 R-random 的胜率、budget_utilization、parse_failures、token 成本。
  4. 差距小于 1 个种子标准差的不写成结论。
  5. 任何 prompt、温度、反馈字段、选优指标的改动都是新版本，不与旧版本同表。

05参照系：Financial Audit Bench

Modus Labs 于 2026-09-30 发布 Financial Audit Bench（FAB），评测 AI agent 能否独立完成审计底稿。它与我们的问题结构相似：长程任务、有限工具、有限调用次数、最终交付一个可被检查的产物。FAB 的设计选择值得逐条对照。

任务
一个任务 = 一份底稿。8 个审计领域、45 份底稿、6 套账套。agent 拿到固定的数据室（约 180 个文件）、一个 bash 工具、最多 200 次模型调用，不能中途索要额外信息。
数据
全部合成。6 套账套由约 250 节点、1,000 边的计算图生成，所有文件数字互相勾稽。种子值来自真实审计的聚合统计，带差分隐私保证。
评分
每份底稿约 10 条检查，由持证审计师写参考答案、10 年以上资深复核。优先确定性检查，只在答案合法可变时用 LLM judge。按行键和列名定位，不按单元格地址。
指标
strict pass（全部检查通过）、partial credit（通过比例）、pass@k、pass^k，每任务跑 8 次。主图横轴是每次运行的美元成本。
结论
"低可靠性，尽管 partial credit 很高。" 最好的模型 strict pass 69.2%；判断密集的领域几乎全军覆没：收入 8%，应收 4%。
和我们的对应关系。FAB 说"partial credit 高、strict pass 低"，我们说"Test 夏普高、Val 分位低"。两者都是：存在一个讨好的指标，和一个说真话的指标；benchmark 的全部价值在于把后者做成主指标。FAB 比我们多走的一步，是把可靠性和判断力也变成了可测量的东西。

06未来方向：按 FAB 的五条设计原则展开

下面每一节先给 FAB 怎么做，再给我们现状，再给要改什么。优先级标在标题上。

原则一：可靠性是指标，不是脚注 P1

FAB 怎么做。每个任务跑 8 次，报 strict pass、pass@k 和 pass^k。它的标题发现正是靠这个得出的：平均分看着不低，但 pass^k 低到不能托付。

我们现状。3–5 个种子取均值。平均 0.33 可能是 5 次都 0.33，也可能是 2 次 0.8、3 次 0.02。前者是稳定地差，后者是偶尔很好但不可靠。均值把两者混在一起。

要改什么。定一条通过线：该次运行的 percentile_val 超过 R-random 在同任务上的中位数。pass@1 = 种子里通过的比例，pass^k = 全部种子都通过。在 score_against_oracle.py 中加两列。种子数从 5 提到 8，与 FAB 对齐。

原则二：奖励有证据边界的结论，惩罚无依据的签字 P1

FAB 怎么做。rubric 里有一类"专业判断"检查，明确给"withholding an overall conclusion"和"not claiming unsupported follow-up"加分。一份底稿把数字全算对但在证据不足时强行签字，仍然不通过。

我们现状。SYNTH_RW 是零漂移随机游走，设计目的是测 agent 会不会追噪声。但它仍按 percentile_val 打分。在纯噪声上分位数靠前，恰恰说明 agent 在追噪声。这个任务想惩罚的行为，评分却在奖励。

要改什么。agent 最终输出多一个结构化字段 recommend_deploy: bool。在 SYNTH_RW 上，false 算通过，true 算失败，不看夏普。这是确定性检查，不需要 LLM judge。之后可扩展到真实任务：当 Val 夏普低于某阈值时，agent 仍建议部署就扣分。

原则三：合成数据切断记忆，且正确答案精确已知 P1

FAB 怎么做。全部账套由计算图生成，不可能出现在任何训练语料里。因为是自己生成的，每个数字的正确值都已知，rubric 可以写得完全确定。

我们现状。以真实 ETF 为主。LLM agent 几乎都选 120 日动量，但我们分不清这是回测反馈告诉它的，还是训练语料里的教科书答案。这是当前最核心的解释缺口。

要改什么。在 make_synthetic.py 里生成一条序列，埋一个非常规回看窗口（如 37 日）的动量信号。建 oracle，正确答案精确。看 agent 在预算内能否通过反馈收敛到 37 附近。找到了，说明在用反馈；仍选 120，说明在背书。可生成多个不同窗口的变体，形成一个"合成 alpha 套件"。

原则四：任务映射到实际分工，Review 单独测 P2

FAB 怎么做。45 个 fieldwork 任务之外，另有 45 个一一对应的 review 任务，agent 从一份已完成的底稿出发做复核。这是因为真实事务所里"做"和"审"是两个岗位。

我们现状。架构 C 系列都有 Reviewer 组件，但只测过它对整体结果的影响，从未单独测它本身能不能审。

要改什么。构造一组"Val 夏普虚高、Test 很差"的 spec 及其回测报告，让 Reviewer 独立判断是否接受。配平衡的正例。报 Reviewer 的准确率和漏放率。这把架构组件变成可被 benchmark 的对象。

原则五：成本是主图的横轴 P2

FAB 怎么做。主图是 strict pass 率对每次运行美元成本，并对模型调用次数设 200 的硬上限。

我们现状。只记 token 数和 llm_calls，预算只限回测次数，不限推理次数。

要改什么。按模型单价换算成美元，主图画 percentile_val 对成本的 Pareto 前沿。给 llm_calls 加硬上限。

已经一致、不需要动的

  • 优先确定性评分，我们目前全确定性。
  • 按内容而非位置定位：非格点 spec 直接回测取值，对应 FAB 的"按行键找值"。
  • 保存完整轨迹：runs.jsonl 带每步 spec 与 best-so-far。
  • 任务等权汇总。

汇报方式的一个改动

FAB 的标题数字是整体 69%，但真正有信息量的是分领域数字（收入 8%、应收 4%）。我们的汇总规则只报跨任务均值。建议同时报每个 tier 的均值和最差任务，否则 SYNTH_RW 这类任务的信号会被 SPY 的高分摊掉。

执行顺序。先做原则一、二、三，并在 core 套件上跑一轮 8 种子的多任务结果。原则四、五等有了第一轮数据再决定。每一步都是新版本，不与旧表混排。
